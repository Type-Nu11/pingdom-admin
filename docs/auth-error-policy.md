# API 인증 오류 처리 기준

관련 이슈: #159

## 공통 판단

관리자·상점주 훅과 관리자 알림 Provider는 `src/api/authError.ts`의
`shouldClearAuth(error)`로 인증 해제 여부를 판단한다. 함수는 판단만 반환하며,
실제 해제는 기존 `clearAuth()` 호출 위치에서 수행한다.

| 오류 | 로그인 상태 |
| --- | --- |
| 일반 API의 최종 401 | 해제 |
| 일반 API의 403 | 유지, 해당 기능의 권한 오류로 처리 |
| 토큰 갱신 실패의 401 또는 403 | 해제 |
| 400, 404, 409, 429, 5xx | 유지 |
| 네트워크·시간 초과·취소·일반 JavaScript 오류 | 유지 |

응답 HTTP 상태, 정규화된 `status`, `category` 순서로 판단한다.
HTTP 상태가 없는 경우 `unauthorized`, 또는 갱신 실패의 `forbidden`만 해제한다.
`INVALID_TOKEN` 응답 코드만으로는 해제하지 않는다. 예를 들어 500 응답에 이 코드가
있어도 서버 오류를 인증 만료로 취급하지 않는다. 오류 안내 문구는 기존 정책을 유지한다.

## 유지하는 경계

- `customAxios`가 401 갱신·재시도, 갱신 사용자 일치 검사, 이전 세션 응답 취소를 담당한다.
- 갱신 실패 시 저장된 인증을 정리하는 인터셉터의 책임은 유지한다.
- 화면별 요청 순서·언마운트 검사, 작업 성공 후 재조회 실패 처리는 변경하지 않는다.
- 명시적 로그아웃, 로그인 화면 및 보호 경로의 세션 정리는 API 오류 판단과 별개다.
- 메시지를 만드는 함수 내부에서도 인증 해제를 호출하는 기존 구조는 유지한다.

## 검증

`tests/auth-error-policy.test.mjs`는 상태·응답 코드·분류 충돌과 취소 오류를 검사한다.
실제 Axios 인터셉터를 거쳐 관리자 탐색 후보, 상점주 온보딩, 관리자 알림에 같은 오류를
전달하여 일반 API/갱신 오류 및 계정 전환 후 늦은 401의 처리 결과를 비교한다.
네트워크 요청은 테스트 어댑터로 대체하므로 실제 서버 데이터는 변경하지 않는다.

전체 회귀 검증은 `npm test`, 정적 검증은 `npm run lint`와 `npm run build`로 실행한다.
