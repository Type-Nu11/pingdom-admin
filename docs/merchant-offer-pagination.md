# 상점주 혜택 서버 페이지네이션 (#160)

## 적용 범위

혜택 관리 화면의 getAllMerchantOffers 전체 선조회를 제거했다. 프로필의 연결 장소를 확인한 뒤 현재 장소·상태·페이지에 해당하는 20건만 조회한다. 연결 장소가 없으면 필터 없는 전체 목록 요청을 보내지 않는다.

2026-09-16 공개 Merchant OpenAPI 기준 GET `/merchant-owner/offers`는 page(1부터), limit, placeId, status(DRAFT/PUBLISHED/CLOSED)를 지원한다. 전체 상태는 status를 생략한다. 소유하지 않은 장소는 서버에서 빈 목록을 반환한다. 웹의 장소 선택은 프로필에 있는 장소만 허용하며 서버 권한 검사를 대신하지 않는다.

응답의 offers, totalElements, totalPages를 그대로 사용하고 현재 페이지에 추가 필터·정렬·slice를 적용하지 않는다. 서버가 반환하는 순서를 유지한다. 상세 조회 결과는 목록에 삽입하지 않으며 목록 전체 건수를 배열 길이로 계산하지 않는다.

## 상태와 변경 요청

- 장소·상태 변경 시 1페이지로 이동한다. 같은 필터·페이지 선택은 무시한다. 페이지·상태 필터 변경은 이전 상세만 해제하며 작성 중인 새 혜택 폼은 보존한다. 장소 변경·새 혜택·등록 성공 등 명시적 초기화는 기존대로 유지한다.
- 같은 장소·필터의 재조회 중에는 이전 페이지 수를 유지해 페이지네이션을 제거하지 않는다. 이전 목록·전체 건수는 현재 결과로 노출하지 않는다. 요청 후 원래 페이지 버튼으로 포커스를 복구하며, 마지막 페이지에서 다음 버튼이 비활성화되면 현재 페이지 버튼으로 이동한다. 사용자가 다른 요소로 이동한 경우 포커스를 빼앗지 않는다.
- 늦은 목록·상세·프로필 응답은 현재 요청을 덮어쓰지 않도록 요청 번호로 무효화한다.
- 공개·종료·초안 생성 성공 후 현재 조건을 재조회하며, 새 항목을 현재 필터에 강제로 삽입하거나 임의로 첫 페이지로 이동하지 않는다.
- 마지막 페이지가 범위를 벗어나면 서버 totalPages에 맞춰 한 번만 보정 요청한다. 전체 이력을 순회하지 않는다. 계속 변하는 데이터는 수동 재조회로 확인한다.
- 변경 성공과 목록 재조회 실패를 분리한다. 성공 안내를 유지하고 목록 오류와 재조회 버튼을 표시하므로 성공한 mutation을 재전송할 필요가 없다.
- mutation 중에는 중복 제출과 장소·상태·페이지·상세 전환을 막는다. 기존 혜택 종료 확인 절차는 유지한다.
- 실패를 0건으로 표시하지 않는다. 서버 건수가 아직 없으면 확인 중으로 표시하고 오류 상태에서는 빈 결과 안내 대신 재조회 UI를 보여준다.

## 합성 성능 비교

실서버 호출 없이 동일한 5,000건(장소 2개)의 합성 데이터로 측정했다. 변경 전은 실제 API 함수를 사용해 100건씩 모든 페이지를 병렬 선조회한 뒤 선택 장소의 20건을 추출하는 기존 알고리즘이다. 변경 후는 실제 useMerchantOffers 훅을 렌더링해 현재 장소 20건을 조회했다. 프로필 조회를 포함해 준비 시간을 측정하고, 요청 수/응답량은 Offer 목록만 집계했다.

| 측정 항목 | 기존 | 변경 후 |
| --- | --- | --- |
| 목록 요청 수 | 50 | 1 |
| 비압축 JSON 응답 합계 | 2,896,327 bytes | 11,560 bytes |
| 데이터 준비 시간(실행 1회) | 48ms | 44ms |

요청당 고정 20ms 지연의 메모리 어댑터를 사용했으며 네트워크 대역폭·압축·브라우저 연결 제한·서버 처리 시간은 재현하지 않았다. 이 시간은 화면 paint 시간이나 운영 성능 수치가 아니며 반복 실행 시 달라진다. 결과의 주요 근거는 전체 페이지 수에 비례하던 요청/전송량이 현재 페이지 크기로 제한된 점이다.

재현: `node --test tests/merchant-offer-pagination.test.mjs`. 테스트 출력의 Offer benchmark를 확인한다. 실제 초기 표시 시간은 운영 계정·데이터로 별도 측정해야 한다.

## 다른 전체 선조회 조사

- useMerchantCampaigns의 캠페인·브랜드 전체 선조회는 남아 있다. 이번에는 해당 필터/브랜드 선택 의존성 계약을 바꾸지 않았다.
- 통합 신청의 getAllMerchantPlaceApplications 사용도 별도 흐름이며 혜택 페이지 전환과 묶어 수정하지 않았다.
- useMerchantStore의 요약 조회는 기존의 제한된 목록 요청을 유지한다. API 함수의 기존 page/limit 호출 호환성은 유지했다.

즉 이번 작업은 #160에 구체화된 Offer 전환이며, 웹의 모든 전체 선조회를 없앴다는 의미가 아니다.

## 검증 범위

- 단위/훅: 첫 페이지 단일 요청, 서버 전체 건수, 필터 초기화, 장소 전환, 응답 역전, 오류/빈 결과/재시도, 상세와 목록 분리, 마지막 페이지 보정, mutation 중복 차단 및 성공 후 재조회 실패.
- `node tests/browser/merchant-offers.mjs`: 실제 MerchantOfferPage와 합성 응답으로 Chromium 1280/390px 페이지 이동·필터·장소 선택·공개 후 필터 이탈·가로 넘침·스크린샷 확인. 같은 필터 재선택의 요청 생략, 페이지·필터 전환 시 새 혜택 입력 보존, 키보드 페이지 이동 후 포커스 복구, 로딩 중 포커스 이동 존중, 목록 실패 시 페이지네이션 유지·재시도를 검증한다. mutation은 모의 어댑터에서만 처리한다.
- 기존 상세 로딩 회귀 테스트도 유지하며 모의 상세에 실제 계약의 placeId를 포함했다.
- 미수행: 실제 계정의 권한·공개·종료·쿠폰 처리, 실서버 초기 paint 성능, 운영 배포, Safari/Firefox.
