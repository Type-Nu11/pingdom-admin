# 장소 정보 반박 심사 응답 및 재조회 보호 (#300)

## 확인된 계약

- 2026-10-19 KST 공개 [admin Swagger](https://www.typenull.xyz/v3/api-docs/admin) HTTP 200을 확인했다.
- 신고 목록 GET은 PlaceInformationReportPageResponse, 상세 GET과 신고 검토 POST는 PlaceInformationReportResponse를 반환한다.
- 반박 검토 POST `/admin/place-information-reports/{reportId}/disputes/{disputeId}/review`는 **PlaceInformationDisputeResponse 한 건**을 반환한다. 신고 전체가 아니며 disputes 배열도 없다.
- 기존 웹은 이 POST를 PlaceInformationReport로 선언하고 신고 전체 state에 저장했다. 상세의 disputes.length/map 접근이 깨질 수 있는 응답 계약 오류다. 새 API를 추가하거나 서버 검토 정책을 바꾸는 작업이 아니다.

## 변경

- 기존 PlaceInformationDispute 타입을 API에 사용한다. 신고·반박 ID와 반박 상태를 확인하고 대상 반박만 교체한다. 신고 본문·증빙·다른 반박은 유지한다.
- 저장 후 목록과 신고 상세를 다시 GET하여 서버가 변경한 신고 상태까지 반영한다. 선택된 신고가 필터 목록에서 사라져도 방금 처리한 상세는 유지한다.
- 일반 POST 실패는 검토 사유를 유지한 저장 오류다. 권한 실패는 이전 상세를 숨긴다. HTTP 성공 이후 GET 실패는 저장 실패로 표시하지 않는다. 모달을 닫고 “검토 결과는 저장됐지만 최신 조회에 실패했다”고 안내한다. 저장 직후 목록 403으로 상세가 숨겨져도 저장 결과와 GET 재시도 경로는 유지한다.
- 최신 조회 실패 후에는 표시된 상세가 재검토 가능한 최신 상태라고 가정하지 않는다. 검토를 비활성화하고 ‘최신 정보 다시 조회’에서 목록·상세 GET만 재시도한다. 둘 다 성공하면 다시 검토할 수 있다. 성공 토스트가 사라져도 재조회 안내는 유지한다.
- 응답 형식이 다른 성공 POST를 신고 객체로 억지 변환하지 않는다. canonical 상세 GET으로 확인하며, 그 조회도 실패하면 이전 상세를 읽기 전용으로 유지한다. 누락된 disputes를 임의의 빈 배열로 만들어 ‘반박 없음’이라고 표시하지 않는다.
- 초기 로딩·정상 빈 목록·조회 실패·이전 목록을 구분한다. 일반 목록 재조회 실패는 이전 건수를 보존하고 표시한다. 401/403은 이전 결과를 숨기고 기존 인증 해제 정책을 유지한다.
- 요청 번호·선택 버전·계정/역할·인증 세션·컴포넌트 생명주기로 늦은 응답을 차단한다. 이전 작업의 결과가 새 신고 상세를 덮거나 새 계정의 검토 모달을 닫고 입력을 지우지 않는다.
- 공용 AppDialog의 포커스 이동/복귀·Tab 트랩·Escape/배경 클릭 보호를 사용한다. 판정 근거 필수 입력, 미저장 입력 보호, 저장 중 닫기와 중복 제출 차단은 유지한다.

## 검증 경계

검증한 흐름은 목록 선택 → POST review의 status/reviewReason → 반박 단건 응답 → 대상 반박 갱신 → GET 목록/상세 → 최종 화면이다. HTTP 계약은 공개 Swagger로, 웹의 요청·응답·상호작용과 상태 보호는 합성 테스트로 확인했다. 인증된 실서버 심사, DB 반영, 서버 런타임 로그·배포 QA를 확인한 것은 아니다.

실데이터의 수용·반려·신고 상태 변경은 실행하지 않았다. Docker·전체 release browser suite·Safari/Firefox·실기기 터치·스크린리더는 미수행이다. 외부 폰트 CSS를 빈 응답으로 처리하므로 스크린샷은 운영 폰트/아이콘의 픽셀 검증이 아니다. 다른 증빙·재확인 패널까지 같은 비동기 보호 리팩토링을 완료했다는 의미도 아니다.

## PR #308 리뷰 지적 1 후속 (2026-10-19 KST)

- 저장 후 목록/상세 중 한 GET의 403이 먼저 도착해 창이 숨겨지고, 나머지 GET이 늦게 완료되면 visible dialog ref가 null이 되어 기존 정리 조건을 통과하지 못했다. 실제 dialog state는 남아 GET 재시도 성공 시 저장한 검토창과 사유가 다시 나타났다.
- 저장 성공 시 함수형 state 갱신으로 제출한 dialog와 동일한 객체만 정리한다. 새 dialog는 닫지 않으며, 미저장 보호 해제도 현재 보이는 제출 dialog가 같을 때만 수행한다. API·인증·권한·심사 정책은 바꾸지 않았다.
- 신고/반박 각각에서 목록 403 우선·상세 403 우선과 다른 GET 지연을 조합한 4개 테스트가 수정 전 모두 실패했고 수정 후 통과했다. 관련 단위/컴포넌트 검사는 39개, 전체 검사는 904개 통과했다.
- 합성 브라우저 1920×1080·1366×768·390×844에서 두 응답 순서의 GET 재시도 후 dialog가 0개이고 POST 수가 그대로임을 확인했다. 새로운 검토창의 사유는 빈 값으로 시작한다. 기존 성공·실패·사유 보존·미저장·pending 보호도 다시 검증했다.
- 이전 계정의 POST를 지연시킨 상태에서 새 계정으로 다른 신고의 검토창을 열어 입력한 뒤, 이전 POST를 완료해도 새 입력이 유지되고 Escape 시 미저장 경고가 표시됨을 실제 공용 보호 컨텍스트로 확인했다.
- 실서버 심사는 실행하지 않았다. 위 결과는 기존과 동일한 격리 합성 환경의 결과이며 운영 저장 성공이나 배포 완료를 의미하지 않는다.
