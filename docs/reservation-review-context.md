# 예약 심사 작업 문맥 복원 (#268)

## 범위

예약 심사(`/reservations/review`)에서 장소 상세(`/places?placeId=…`)로 이동한 뒤
뒤로 돌아오거나 예약 심사 화면을 새로고침할 때, 적용된 필터·페이지·선택 예약을 복원한다.
다른 심사 페이지에 일괄 적용하거나 새로운 API를 추가하지 않는다.

## 저장 규칙

- URL에는 `status`, `placeId`, `page`, `reservationId`만 기록한다.
- 기본값은 심사 대기(`PENDING`), 전체 장소, 1페이지, 선택 없음이다.
- 전체 상태는 `status=ALL`로 기록한다. 기본값은 URL에서 생략한다.
- ID는 양의 안전 정수, 페이지는 1~999999, 상태는 알려진 enum만 허용한다.
  중복 파라미터·잘못된 값은 기본값으로 처리하고 알 수 없는 파라미터는 제거한다.
- 장소명·주소·예약자·메모·반려 사유·첨부 정보는 URL이나 저장소에 보관하지 않는다.
- 검색 폼의 미적용 입력은 로컬 초안이다. 페이지 이동·새로 조회에는 적용된 조건을 사용한다.
  화면을 떠나거나 재로드하면 미적용 입력은 복원하지 않는다.
- 필터·페이지 변경은 브라우저 이력에 추가하고, 행 선택·선택 해제·URL 정규화는 현재 이력을 대체한다.

## 계정과 인증

예약 화면의 history state에 사용자 ID와 역할만 기록한다. 다른 계정 또는 역할이 해당 이력으로
돌아오면 이전 조건과 선택을 초기화한다. 새 탭에 직접 입력한 링크는 소유 이력이 없으므로
새 조회로 취급하고, 실제 데이터 접근은 서버의 권한 검사에 맡긴다.

기존 로그인 복귀 규칙에 예약 심사의 안전한 파라미터만 추가한다. 동일 계정의 인증 복귀에서
문맥을 유지하며, 계정을 알 수 없는 복귀는 장소·예약 ID를 제거하고 다른 계정 복귀는 기존
홈 이동 정책을 유지한다. 토큰·권한 검사·API 인증 계약은 변경하지 않는다.

## 재검증과 실패 처리

1. 복원한 조건으로 목록을 다시 조회한다. 과거 목록/상세를 저장해서 보여주지 않는다.
2. 현재 페이지의 목록에 선택 예약이 있는 경우에만 상세를 조회한다.
3. 목록에서 빠졌거나 상세 상태/장소가 조건과 다르면 선택을 해제하고 이유를 안내한다.
   삭제되었다고 단정하지 않는다.
4. 상세의 403/404 또는 목록 권한 오류에서는 선택을 해제하되 오류 안내를 유지한다.
5. 네트워크/5xx 조회 실패는 빈 결과로 표현하지 않는다. 선택 문맥은 유지하고 목록/상세 재시도를 제공한다.
6. 마지막 페이지가 서버에서 보정되면 URL도 실제 페이지와 맞추고 이전 선택은 해제한다.
7. 늦게 도착한 이전 목록/상세 응답은 새 조건과 선택을 덮어쓰지 못한다.

승인·반려 전에는 현재 목록과 상세의 선택 ID 및 `PENDING` 상태를 다시 확인한다.
기존 중복 제출 방지와 요청 중 모달 닫기 방지를 유지하며, 심사 요청 실패 메시지가
자동 상세 재조회로 사라지지 않게 한다.

## 검증

- `node --test tests/reservation-review-context.test.mjs`: URL 검증, 왕복/재로드,
  미적용 입력, 상태/권한 변경, 목록/상세 실패·재시도, 늦은 응답, 페이지 보정,
  계정 변경, 인증 복귀, 합성 심사 성공·실패를 확인한다.
- `npm run test:reservation-context-browser`: 실제 예약·장소 페이지를 연결한 격리 fixture에서
  1920×1080, 1366×768, 390×844의 레이아웃/가로 넘침과 키보드 장소 이동,
  뒤로가기/재로드, 실패·빈 결과·계정 변경 흐름을 검사한다.
- 실제 운영 API 호출은 차단한다. 브라우저 fixture는 GET 합성 응답만 사용하며,
  심사 제출은 단위 테스트의 명시적인 합성 adapter에서만 검사한다.
- 일반 단위 테스트, 기존 장소 검색 및 심사 모달 브라우저 회귀 검사, lint와 production build도 실행한다.

인앱 확인도 별도 fixture에서 수행한다. 실제 서버의 예약 데이터·권한 변경과 전체 관리자 QA는
별도 검증 대상이며, 이 결과를 실데이터 승인/반려 검증으로 간주하지 않는다.
